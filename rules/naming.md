# Naming Rules (Java, JavaScript, Thymeleaf)

These rules are binding on every code edit in Java, JavaScript, and Thymeleaf templates.

- **Variable names must match their class name.** Always name a variable as the **full** lowercased simple class name. Never abbreviate it, shorten it, or drop a suffix. For example, `UniqueCodeGenerator` → `uniqueCodeGenerator`, not `codeGenerator`. `SubscriptionItemRepository` → `subscriptionItemRepository`, not `productRepository`. `SubscriptionDetailDto` → `subscriptionDetailDto`, not `sub`, `subscription`, or `detail`. **Always include the `Dto` suffix, even when there is no name collision with an entity of the same stem.** Do not drop the `Dto` / `Projection` / `Entity` part of the class name because it looks verbose. This rule applies to fields, constructor parameters, method parameters, local variables, lambda parameters, and **Thymeleaf `th:each` iteration variables** (for example, `th:each="serviceRegion : ${serviceRegions}"`, not `th:each="wh : ${serviceRegions}"`, and `th:each="orderLineDto : ${order.orderLines}"`, not `th:each="line : ${order.orderLines}"`). One category can stay abbreviated: URL query-param *strings* — the `value = "..."` in `@RequestParam` and the raw query-string names built in templates. Those strings are user-facing, and shorter keys make browser URLs more compact. The Java variable bound to the short param must still be fully descriptive. Correct: `@RequestParam(value = "s", required = false) final String sortCode`. Wrong: `@RequestParam(value = "s", required = false) final String s`.
- **No generic single-letter or vague variable names.** Never use names like `v`, `el`, `e`, `x`, `tmp`, `val`, `obj`, `dto`, `proj`, `assoc`, `btn`, `sb`, `pd`, `sw`, `po`, `pt`, `wh`, `ol`, `dr`, `ex`, `err`, `fmt`, `rows`, `list`, `items`, `entries`, `records`, `results`, `data` for locals, lambda parameters, callback parameters, or `th:each` variables — not even when the next line holds the only use of the variable. Always use a name based on the type of the value (`subscriptionPaymentTerm`, `billingPeriod`, `serviceRegion`, `orderLineConflictProjection`, `dateRange`, `dateTimeFormatter`, `stringBuilder`, `subscriptionSummaryDto`). For `String`/primitive iterables, where the type alone is not meaningful, use a name based on what the value represents (`productBullet`, `errorMessage`, `paymentTermId`, `serviceRegionCode`). This rule applies to Java, to JavaScript (including `btn` → `button`, `el` → `element`, `evt` → `event`), and to Thymeleaf. The only acceptable single-letter or short-form names are the conventional integer loop counters (`i`, `j`) and the exception variable in a `catch` block (`e`). The `e` is fine whether or not the body uses it (for example, to log `e.getMessage()`). Bad: `final var v = parseInt(el.value, 10);` Good: `final int quantity = parseInt(input.value, 10);` Bad: `.map(sub -> sub.id())` Good: `.map(subscription -> subscription.id())`. For typed collections, use the plural form of the element class name (`List<UsagePreviewRow>` → `usagePreviewRows`, not `rows`). When the collection comes from a named context (a session attribute, a cache, or a map key), name the variable after the source key. Bad: `final List<UsagePreviewRow> rows = (List<UsagePreviewRow>) session.getAttribute("usageUploadRows");` Good: `final List<UsagePreviewRow> usageUploadRows = (List<UsagePreviewRow>) session.getAttribute("usageUploadRows");`.
- **Verbose converter method names.** A private method that converts one type to another must use the full class name of both the source and the target: `{SourceClassName}To{TargetClassName}`, not an abbreviated form. For example, `orderProjectionToOrderSummaryDto` (not `toSummaryDto` or `orderProjectionToSummaryDto`), and `serviceRegionToServiceRegionDto` (not `toDto` or `serviceRegionToDto`). Both class names must show in full. Then the source and target types are unambiguous at the call site, especially with method references.
